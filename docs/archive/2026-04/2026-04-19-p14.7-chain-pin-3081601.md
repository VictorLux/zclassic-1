# Postmortem — 2026-04-19 chain pin at h=3,081,601 (post-P14.1 canary)

**Status:** root-cause narrowed; first fix landing in this row.
Canary will discriminate between the shortlisted sub-hypotheses.
**Related rows:** P14.1 (dedicated sqlite3 connection — `d67817dd2`,
the *previous* stall fix), **P14.7 (this doc)**, P14.6 (promoted
P12.2 — BLOCK_FAILED_CHILD propagation GC).

---

## TL;DR

P14.1 fixed the BIP30 / SAVEPOINT flush bug. Chain advanced
3,081,408 → 3,081,601 in ~3 min on the canary deploy, then pinned.

The AGENT-2.md brief claimed the FSM transitions `ready → connecting
→ ready: behind_peers` **without ever calling activate_best_chain**.
That claim is *wrong by inspection* —
`activation_request_connect` unconditionally calls
`activate_best_chain` between the `CONNECTING` and the post-connect
state transitions (see
`app/services/src/chain_activation_controller.c:271-317`).

The corrected diagnosis: `activate_best_chain` IS called, but
`find_most_work_chain` returns the current tip, so activate
silent-early-returns at
`lib/validation/src/process_block.c:1915-1916` without logging.
The FSM then completes `CONNECTING → READY (behind_peers)` because
`pindex_best_header` is 2,041 ahead of the tip.

Evidence from `~/.zclassic-c23/node.log` at the time of the stall:

- `activate_best_chain: tip=X most_work=Y` appears **zero** times
  for any height > 3,081,601 — exactly what the silent early-return
  produces.
- `activation: ready->connecting (new_block)` +
  `activation: connecting->ready (behind_peers)` fire continuously
  (~5×/sec) — confirms activate IS getting invoked, just not doing
  anything.
- 313k+ `completed msg 'block'` lines — block bodies ARE arriving.
- Zero `Propagated BLOCK_FAILED_CHILD` or `BIP30` lines in the stuck
  window — no new failure propagation.
- Zero `Boot: cleared BLOCK_FAILED on N blocks above tip` — boot
  sweep at `config/src/boot.c:2197-2220` found nothing to clear.

So the question is: **why does `find_most_work_chain` return the
current tip when peers are 2,041 blocks ahead and blocks are
arriving?**

---

## Question 1 — what filter is excluding the candidates?

`find_most_work_chain` at
`lib/validation/src/process_block.c:403-477` rejects a candidate if
any of:

1. `nStatus & BLOCK_FAILED_MASK` is non-zero (line 418).
2. `block_index_is_valid(pindex, BLOCK_VALID_TREE)` returns false —
   which is equivalent to filter 1 OR `nStatus & BLOCK_VALID_MASK
   < BLOCK_VALID_TREE` (line 424).
3. `pindex->nChainTx == 0 && !(nStatus & BLOCK_HAVE_DATA)` — no
   body yet (line 437-441).
4. Candidate's `nChainWork` does not exceed current `best->nChainWork`
   (line 443-444). `best` starts as the current tip.
5. Ancestry walk from candidate down to `tip_h` finds a
   `BLOCK_FAILED_MASK` on an intermediate block (line 449-465).

For peers to be sending blocks and them all being filtered, at
least one of filters 1/2/3/4/5 must universally reject every block
at h > 3,081,601 whose body has arrived.

Boot-time sweep ran at `tip_height=3,081,408` and cleared
`BLOCK_FAILED_MASK` on all blocks above that tip (see
`boot.c:2197-2220`). The 193-block advance to 3,081,601 added zero
new FAILED propagations (verified by log). So filter 1 and 5 are
unlikely.

Filter 3 is the most interesting. Bodies ARE arriving per the log,
but that doesn't mean `accept_block` successfully sets
`BLOCK_HAVE_DATA` + `nChainTx` on every one. `accept_block`'s
early-returns at
`process_block.c:833-835` drop a block *without* setting
`BLOCK_HAVE_DATA` when:

- `pindex->nTx != 0 && (pindex->nStatus & BLOCK_HAVE_DATA)` — already
  have (harmless)
- `!has_more_work` — candidate's `nChainWork` does not exceed current
  tip

The `!has_more_work` check compares `pindex->nChainWork` against
`tip->nChainWork`. For a block at `h = tip+1`, `nChainWork` should
be `tip->nChainWork + GetBlockProof(pindex)`, which is strictly
greater. Unless the candidate's `nChainWork` is **stale** (e.g. set
when its `pprev->nChainWork` was zero or wrong), in which case the
check fails and the body is silently dropped.

Filter 4 (nChainWork comparison) in `find_most_work_chain` has the
same exposure. Stale `nChainWork` makes the candidate invisible.

`propagate_nchaintx` at `config/src/boot_index.c:1104-1174` only
propagates `nChainWork` when it is currently zero (line 1161
guard: `arith_uint256_is_zero(&b->nChainWork)`). Stale non-zero
values are never corrected.

## Question 2 — likeliest root cause

Ordered by the evidence:

1. **`nChainWork` staleness on blocks above tip** (most likely).
   Heights are periodically re-propagated
   (`msg_headers.c:466-490` logs "Post-activation: re-propagated
   N heights") but `nChainWork` is explicitly *not* re-propagated
   (comment at `boot_index.c:1060`). If a block's `pprev->nChainWork`
   was wrong when the block entered the index, its own
   `nChainWork` stays wrong forever.

2. **Stale `BLOCK_FAILED_CHILD` marks** cleared by accept_block_header
   only within `tip_h - 100`; beyond that, rate-limited to 1
   clear per 300s (`process_block.c:691-698`). For 2,000 blocks
   that's 166 hours to drain. Any runtime propagation (not
   observed this session, but possible) would stick.

3. **Blocks arriving but `!has_more_work`** at accept_block time
   — same root cause as 1 (stale `nChainWork`) — drops the body
   silently before `BLOCK_HAVE_DATA` is set, so filter 3 also
   rejects.

All three share a common remedy surface: observability in
`find_most_work_chain` that reports WHICH filter won, and one
narrow fix for each.

## Fix landing in this row

**Fix 1 — rate-limit split for FAILED_CHILD in
`accept_block_header` (`process_block.c:682-699`).**
`BLOCK_FAILED_CHILD` is a propagation mark, not a real validation
failure. Clearing it does not trigger a re-validate storm because
`connect_block` only fires when the block actually becomes the
candidate tip. Rate-limit stays in effect for
`BLOCK_FAILED_VALID` only.

Before:
```c
if (pindex->nStatus & BLOCK_FAILED_MASK) {
    int tip_h = active_chain_height(&ms->chain_active);
    if (pindex->nHeight >= tip_h - 100) {
        pindex->nStatus &= ~BLOCK_FAILED_MASK;
    } else {
        static time_t last_retry_clear = 0;
        time_t now = time(NULL);
        if (now - last_retry_clear >= 300) {
            pindex->nStatus &= ~BLOCK_FAILED_MASK;
            last_retry_clear = now;
        }
    }
}
```

After: CHILD-only (non-VALID) marks clear without rate-limit.

**Fix 2 — diagnostic logging in `find_most_work_chain`.**
Rate-limited (once per 60s) log when the function returns the
current tip unchanged. Reports the filter counters
(`skipped_failed`, `skipped_invalid`, `skipped_no_chaintx`) and
best_header's state, so the canary reveals the actual production
root cause without another round-trip.

**Fix 3 (deferred to P14.7.1 if canary shows it's needed) —
`nChainWork` re-propagation.** A height-ordered pass that fixes
stale `nChainWork` values (not just zeros). This is a bigger
change with cross-cutting implications for fast-sync's chain
selection, so it waits for canary evidence.

## Question 3 — why did P10.1 + P14.1 tests not catch this?

P10.1's test harness exercises `connect_block` and the
coins_view_cache flush path directly. It does not build a
`block_map` or call `activate_best_chain` — by design,
`find_most_work_chain` is static and not directly exercised in
unit tests. That coverage gap is what this row's RED test
(below) closes.

## Question 4 — invariant for the RED test

"Given a chain where blocks above the tip have body data
(`BLOCK_HAVE_DATA | nChainTx > 0`) and clean validation status
except for a stale `BLOCK_FAILED_CHILD` mark whose parent is not
failed, `find_most_work_chain` must return a chain tip strictly
above the current tip." The test exercises the accept_block_header
retry path for an existing pindex and asserts that the CHILD-only
mark clears without rate-limit.
