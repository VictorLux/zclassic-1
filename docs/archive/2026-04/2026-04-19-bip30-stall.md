# Postmortem — 2026-04-19 BIP30 chain stall at h=3,081,407

**Status:** root-cause identified.  
**Related rows:** P7.2 (partial-application rewind), P8.9 (boot-time
sweep, hotfix), P8.10 (proposed second hotfix, SUPERSEDED), P10.1.1
(deterministic repro, `1243e1766`), **P10.1.2 (this doc)**, P10.1.3
(RED regression test — next), P10.1.4 (minimal fix — blocked on
P10.1.3), P10.1.5 (live-node canary — blocked on P10.1.4).  
**Scope:** investigation + invariant only. No code lands in this row.

---

## TL;DR

`disconnect_block` in `lib/validation/src/connect_block.c:639` calls
`coins_map_erase(&view->cache_coins, &tx->hash)` to drop each
transaction in the disconnected block from a scratch coins view that
wraps `coins_tip` as backing. **This erase does not propagate to the
backing store.** The `coins_view_cache` flush path (`cvc_batch_write`
in `lib/coins/src/coins_view.c:255` and the SQLite equivalent at
`lib/storage/src/coins_view_sqlite.c:664`) only writes entries marked
`COINS_CACHE_DIRTY`. An erased entry is non-DIRTY (it is gone), so the
coinbase row survives in `coins_tip` and, after the next flush, in
SQLite's `utxos` table — even though the tip has rewound past the
block that created it.

On the next `connect_block` retry the BIP30 check at
`connect_block.c:219-233` calls `coins_view_cache_have_coins` for the
new block's coinbase txid. The cache miss falls through to the SQLite
backing, finds the stale row, sees the coins are not pruned, and
rejects with `bad-txns-BIP30`. Every retry re-propagates
`BLOCK_FAILED_CHILD` to every header-tip descendant, which in turn
is what drove the 2026-04-19 live node from 5.9 GB RSS to the cgroup
high-water mark in 2h51m.

P8.9 (`b875152da`) patched the *one-time* post-P7.1 partial-application
leak at boot. That fix was necessary but incomplete: as soon as a
steady-state `disconnect_tip` fires for any reason (reorg,
`bad-txns-inputs-missingorspent` auto-recovery, manual `invalidate`)
the same shape is recreated at runtime and the sweep — which is
dormant when `max_utxo_height == tip_height` — never runs again.

## Question 1 — the EXACT path that took chain 3,081,408 → 3,081,407

### The two production callers of `disconnect_tip`

`grep -n 'disconnect_tip(' lib/validation/src/process_block.c` returns
exactly two live sites:

- **`process_block.c:1929`** — reorg path inside `activate_best_chain`.
  Emits `EV_REORG_START` (`process_block.c:1924`) *before* the first
  disconnect and logs `"activate_best_chain: reorg depth ..."`. The
  live node logs for 2026-04-19 22:10 → 01:01 show NEITHER the event
  NOR the log line, so the first site can be excluded.

- **`process_block.c:2082`** — the `bad-txns-inputs-missingorspent`
  auto-recovery inside the `activate_best_chain` error handler. Fires
  when `state->reject_reason == "bad-txns-inputs-missingorspent"` has
  accumulated `s_utxo_fail_count >= 5` for the **same** `nHeight`. It
  prints `"[recovery] N UTXO failures at h=X — disconnecting tip
  h=Y to retry\n"` and then calls `disconnect_tip(&ds, ...)`.

### Why site 2 is the triggering path

The live node successfully connected `h=3,081,408` at boot and then
kept advancing header-tip downloads from peers. The header tip reached
`≥3,082,600` while the chain tip was at `3,081,408`. Blocks after
3,081,408 kept flowing through `activate_best_chain`.

If any block at `h=3,081,409` or later failed with
`bad-txns-inputs-missingorspent` five times in a row at the same
height — a plausible outcome whenever an input prevout references
something that lives only in the cache and the cache is flushed or
cleared between retries — the recovery path at `process_block.c:2082`
fires **silently from the operator's perspective**. `[recovery]` goes
to stderr; the binary runs under `systemd --user`, whose stderr is
routed to journalctl; the coordinator's `systemctl status` output in
AGENT-2.md only shows the last 40 lines. The evidence block in
AGENT-2.md is not a `journalctl -u zclassic23 -b` capture, so the
`[recovery]` line may already have scrolled.

We cannot *prove* this path fired in the live incident without a full
journal capture. What we **can** prove is: if `disconnect_tip`
executed for any reason (site 1, site 2, or any future third caller)
the post-disconnect shape is the one the node was trapped in. The
fingerprint is state-, not path-, dependent, and the state is
reproducible on a fixture (see `test_chain_stall_repro.c`,
`1243e1766`).

### The state transition that matters

Regardless of which caller runs `disconnect_tip`, the tip-regress
sequence is:

```
t0  coins_tip.hash_block = H(3081408)
    coins_tip.cache_coins[coinbase_3081408] = {unspent, DIRTY|FRESH or (after flush) absent}
    SQLite utxos: coinbase_3081408 row present         [if flushed before t1]
    SQLite node_state.coins_best_block = H(3081408)    [if flushed before t1]
    active_chain.tip = pindex(3081408)
    
t1  disconnect_tip(...) — any caller
    ├─ scratch = coins_view_cache wrapping coins_tip
    ├─ disconnect_block(&blk_3081408, ..., scratch, ...)
    │     for i = num_vtx-1 .. 0:
    │       if i > 0: restore spent inputs (DIRTY, OK)
    │       coins_map_erase(&scratch.cache_coins, &tx.hash)   ← BUG
    ├─ coins_view_cache_flush(scratch)  — flushes scratch DIRTY
    │     entries into coins_tip via cvc_batch_write, which
    │     does NOT see the erased coinbase (it's gone from
    │     scratch's map, no DIRTY flag, no DELETE signal)
    ├─ update_tip(ms, pindex_3081407) — csr commits the tip
    │     move; coins_tip.hash_block ← H(3081407)
    └─ SQLite is untouched until next flush_coins_if_needed
    
t2  coins_tip.hash_block = H(3081407)            ← tip rewound
    coins_tip.cache_coins[coinbase_3081408] = {unspent}   ← STALE
    SQLite utxos: coinbase_3081408 row still present      ← STALE
    SQLite node_state.coins_best_block = H(3081407)       [next flush]
    active_chain.tip = pindex(3081407)           ← rewound
    
t3  activate_best_chain retries connect 3081408.
    connect_block(blk_3081408).BIP30 check:
    for each tx in blk_3081408:
        coins_view_cache_have_coins(view, &tx.hash)
        └─ view is a fresh scratch; not in cache_coins;
           falls through to backing = coins_tip.
        └─ coins_tip has coinbase_3081408 as unspent.
        └─ RETURN TRUE → BIP30 trips → reject.
    
(loop forever, re-marking BLOCK_FAILED_CHILD each pass)
```

The regress in `getblockcount` output is the `active_chain.tip = pindex(3081407)` field at t2. `update_tip` drove it via
`process_block_commit_tip(...)` → `csr_commit_tip(...)` →
`active_chain_set_tip(...)` at `chain_state_repository.c:343`.
Event-level, it emits `EV_TIP_UPDATED h=3081407`. The node also prints
`"[csr] commit_tip h=3081407 reason=..."` at
`chain_state_repository.c:336`, and logs
`"disconnect_tip: update_tip rejected ..."` only on FAILURE of the
commit. The observed evidence is consistent with a *successful* tip
move — hence no stderr breadcrumb.

## Question 2 — WHY BIP30 trips after P8.9's strengthened sweep ran

### What P8.9 actually does

`coins_view_sqlite_open` at `lib/storage/src/coins_view_sqlite.c:207`
computes `max_utxo_height` and `tip_height` from SQLite, then:

- if `max_utxo_height <= tip_height` → accept (sweep dormant).
- if `max_utxo_height == tip_height + 1` and ≤ 32 overshoot rows →
  run `coins_view_sqlite_rewind_above_tip` which deletes rows at
  `utxos.height > tip_height`, plus (P8.9) cross-references the
  `transactions` table to purge rows whose `tx_index.block_height >
  tip_height` even when their `utxos.height` is ≤ tip (the
  orphan-coinbase shape).

### Why the sweep goes dormant at steady state

After boot the node reaches
`max_utxo_height == tip_height == 3,081,407`. The sweep is gated by
`max_utxo_height > tip_height`. From that point on, until the next
restart, **no sweep fires**.

### Re-creating the stale state at runtime

`disconnect_block.c:639`'s `coins_map_erase` leaves the just-
disconnected coinbase in `coins_tip` (because the scratch cache was
never populated with it). Two flush cycles later — whenever
`flush_coins_if_needed` decides to write — that coinbase lives in
the SQLite `utxos` table at `height ≤ tip_height`. The sweep's
boot-time condition is satisfied, so even if the node restarts in
this state, the sweep does not fire: `max_utxo_height` equals
`tip_height`, not exceeds it.

So the sweep is effective once at boot for the post-P7.1 shape, and
never again. Every `disconnect_tip` call re-instates the bug at
runtime without any boot-visible indicator.

### Bitcoin Core comparison

The equivalent Bitcoin Core path is `CCoinsViewCache::BatchWrite` at
`bitcoin/src/coins.cpp`. When a pruned child entry is promoted to the
parent, the parent's entry is erased via `cacheCoins.erase(it)`. At
parent → LevelDB flush time, `CDBBatch::Erase` writes an actual
DELETE to the database for that key. In our code we DO erase from
`cache_coins` (matching commit `172356135`'s fix pattern for
parent-cache pruned entries) — but our SQLite flush is
DIRTY-driven, so an erase on a non-DIRTY entry produces no SQLite
write. The two paths have the same shape but different persistence
semantics, and the ZClassic C23 implementation silently skipped the
DELETE that Bitcoin's LevelDB batch emits automatically.

## Question 3 — the invariant that should have been enforced

**Invariant (for the coins view, both cache and backing combined):**

> For every transaction T that appears in the coins view — whether
> resident in `coins_tip.cache_coins` or in the SQLite `utxos` table
> — the block B that created T's outputs must be on the active chain
> (i.e. `active_chain_contains(&ms.chain_active, B)` must be true).
>
> Equivalently: after `disconnect_block(B)` completes and the
> enclosing `disconnect_tip`'s `coins_view_cache_flush` runs, every
> output created by any transaction in B must either:
>   - be absent from `coins_tip.cache_coins`, AND
>   - be absent from SQLite `utxos` after the next
>     `flush_coins_if_needed` (i.e. the next flush must emit a DELETE
>     for it).

**Where to enforce it:**

- **At the boundary between `disconnect_block` and the scratch flush
  (`connect_block.c:639`).** The erase must be replaced by a DIRTY
  pruned tombstone — `coins_view_cache_modify(view, &tx->hash)`
  followed by clearing all vout entries (or simply
  `coins_spend`-ing them one by one) and leaving the DIRTY flag set.
  On flush, `cvc_batch_write` sees a DIRTY+pruned entry and
  propagates it into `coins_tip`. On the next `coins_tip` flush,
  `coins_view_sqlite_batch_write_ex`'s pruned branch at
  `lib/storage/src/coins_view_sqlite.c:667` emits `DELETE FROM utxos
  WHERE txid=?` — exactly the write that should have happened when
  the block was disconnected.

- **As a debug assertion, after every `disconnect_tip`:** walk the
  disconnected block's txs and assert `!coins_view_cache_have_coins`
  for each txid. In release builds this becomes a metric bump +
  event rather than an abort, so regressions surface in telemetry
  rather than crashing a production node. This is the "invariant
  assertion" the P10.1.4 row calls for — not a consensus rule, a
  **state-consistency** rule on a data structure we own.

**Note on disconnect_block's non-coinbase tx handling.** For non-
coinbase txs the current code also calls `coins_map_erase(&tx->hash)`
at `connect_block.c:639`. The same bug applies, but the impact is
subtle: non-coinbase tx outputs are typically spent by later blocks,
so by the time we disconnect the creating block those outputs are
already absent from the coins view (`coins_spend` → pruned tombstone
via `update_coins_with_undo`). The bug is silent there because the
DIRTY tombstone is produced elsewhere. For a disconnected block whose
non-coinbase tx outputs were *not* yet spent by a later block, the
same leak would occur — but in practice such a shape only matters
transiently during a reorg and is overwritten by the incoming chain's
writes. The BIP30 failure surface is specifically the coinbase path
because coinbase outputs are the only ones that BIP30 checks against.

## Question 4 — why existing tests didn't catch this

Three test files exercise `disconnect_block`:

1. **`lib/test/src/test_chain_rollback.c:170`** — iterates 20
   coinbase-only blocks, disconnects all, asserts
   `!coins_view_cache_have_coins(&cache, &blocks[h].vtx[0].hash)` at
   `test_chain_rollback.c:187` and `cache.cache_coins.size == 0` at
   `test_chain_rollback.c:196`.

2. **`lib/test/src/test_reorg_safety.c:139`** — 50-block two-chain
   reorg; asserts via `no_coins_present` and the incremental
   commitment that disconnected A-chain coinbases are absent after
   `disconnect_block`.

3. **`lib/test/src/test_validation.c:1041`** — narrow error-path
   tests (undo count mismatch, pathological `prevout.n`).

**All three operate on a single `coins_view_cache` with a NULL
backing view**, e.g. `test_chain_rollback.c:131`:

```c
struct coins_view_cache cache;
struct coins_view null_view;
memset(&null_view, 0, sizeof(null_view));
coins_view_cache_init(&cache, &null_view);
```

With a NULL backing, `coins_view_cache_have_coins` after a
`coins_map_erase` correctly returns `false` because:

- `cache.cache_coins.find(txid)` → miss (erased).
- Falls through to `coins_view_get_coins(&cache.base = null_view, ..., &tmp)`
  at `coins_view.c:193`.
- `null_view.vtable == NULL` → `coins_view_get_coins` returns false
  (`coins_view.c:84`).

The tests pass because **the backing view can never reveal the leak
— it doesn't exist**. The bug only manifests when the backing view
*does* hold data the cache lies about, which is exactly the scratch-
wrapping-`coins_tip` shape that `disconnect_tip` uses in production.

### The test that would have caught this

A test that mirrors the production call shape: a PARENT cache
representing `coins_tip`, populated via `update_coins`; a SCRATCH
cache wrapping the parent as backing; `disconnect_block` on the
scratch; a flush of the scratch into the parent; and finally the
assertion that the parent no longer reports
`coins_view_cache_have_coins` for the disconnected coinbase.

In pseudocode:

```c
// Parent — the "coins_tip" proxy.
struct coins_view_cache parent;
coins_view_cache_init(&parent, &null_view);
update_coins(&blk.vtx[0], &parent, nHeight);

// Parent itself is a coins_view for backing purposes.
struct coins_view parent_view;
coins_view_cache_as_view(&parent_view, &parent);

// Scratch — the disconnect_tip scratchpad.
struct coins_view_cache scratch;
coins_view_cache_init(&scratch, &parent_view);
disconnect_block(&blk, &vs, &bi, &scratch, &empty_undo);
coins_view_cache_flush(&scratch);

// THIS is the assertion that fails today.
ASSERT(!coins_view_cache_have_coins(&parent, &blk.vtx[0].hash));
```

Today that assertion fails — the parent still holds the coinbase.
That is the shape of the P10.1.3 regression test. It should be
added as a new case in `test_reorg_safety.c` (same domain) or a new
small file, and named after the invariant:
`test_disconnect_block_purges_coinbase_from_backing`.

### Why the test was structured that way

The null-backing shape is faster and sufficient for testing
`disconnect_block`'s undo-data handling and commitment arithmetic,
which is what the two rollback tests were written for. The authors
treated `coins_map_erase` as the post-condition (not a bug), and the
cache-only assertion verified that post-condition. The real bug is
one layer up in the data model: the scratch → parent → SQLite flush
chain does not honour erase as a delete signal, and that hides behind
any cache-only test.

P10.1.3 closes this specific gap with a RED regression test that
models the scratch-wrapping shape directly.

## Follow-ups (out of scope for P10.1.2; filed here for traceability)

- **P10.1.3 — RED regression test** using the three-layer shape above,
  committed to main and failing on current HEAD. Test name should
  describe the invariant: `test_disconnect_block_purges_coinbase_from_backing`
  (or similar).
- **P10.1.4 — minimal fix.** Replace
  `coins_map_erase(&view->cache_coins, &tx->hash)` at
  `connect_block.c:639` with a DIRTY-pruned-tombstone write. Add a
  debug-only assertion after `disconnect_tip` that walks the
  disconnected block's txs and asserts `!coins_view_cache_have_coins`
  on the parent.
- **P10.1.5 — live-node canary.** Rhett runs `make deploy`; the
  chain should advance past `h=3,081,407` within 120s; monitor
  `EV_BLOCK_CONNECTED` for 24h and confirm RSS plateaus instead of
  climbing.
- **Phase 2 — property test.** Once the fix lands, add a property
  test that random-walks through connect/disconnect pairs across a
  multi-layer cache hierarchy and checks the invariant on every step.
  This catches any future `disconnect_block` regression and keeps the
  invariant locked in.

## Non-goals

- **BIP30 itself.** BIP30 is doing exactly what it should: protecting
  against duplicate coinbase overwrite. The `REJECT_INVALID` at
  `connect_block.c:227` is correct. The node's crime was lying to
  BIP30 about which coinbases existed.
- **Boot-time sweep.** P8.9 remains the right belt-and-braces guard
  against post-P7.1 partial-application debris left over from older
  incidents. It is not the root-cause fix and should not be extended
  to cover the runtime case — the runtime case belongs in
  `disconnect_block` itself.
- **Consensus divergence from zclassicd.** The fix does not change
  consensus; it brings the data structure back into sync with
  consensus-level assumptions that already hold in zclassicd
  (LevelDB's `Erase` semantics make the equivalent bug impossible
  in the legacy code).
