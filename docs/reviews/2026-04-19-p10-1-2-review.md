# Review of P10.1.2 root-cause writeup (5279752d1)

## Reviewer: Agent-3

## Verdict: CONCUR_WITH_NOTES

The mechanism and root cause in `docs/postmortems/2026-04-19-bip30-stall.md`
are correct and verified against the code at every cited line. The
writeup honestly flags what it cannot prove (the exact live-node caller
of `disconnect_tip`) and confines the certain claims to state shape.
Notes below are sharpenings, not disagreements.

## Question 1 (regress path 3,081,408 → 3,081,407)

**Concur with notes.**

Verified the writeup's claim about caller counts:
`grep -n 'disconnect_tip(' lib/validation/src/process_block.c` returns
exactly two live call sites — `:1929` (reorg) and `:2082` (recovery).
`recover_from_disconnect_failure` at `:1738` is *not* a third caller —
it calls `coins_view_cache_clear` + `process_block_commit_tip` and
never re-enters `disconnect_tip` itself. The writeup's exclusion of
site 1 by log absence (no `EV_REORG_START` at `process_block.c:1924`,
no `"activate_best_chain: reorg depth ..."` line) is sound given the
evidence available.

Site 2 remains *inferred*, not *proven*. The writeup acknowledges this
directly (lines 83-85): AGENT-2.md's 40-line `systemctl status` crop
is not a full `journalctl -u zclassic23 -b` capture, so the
`[recovery] N UTXO failures ...` stderr line may have scrolled. For
P10.1.3 design this gap does not matter — the regression test models
the post-`disconnect_tip` state shape (which is path-independent), not
the exact caller. But for P10.1.5 live-node canary I'd add a stderr
breadcrumb inside `disconnect_tip` itself that names the caller (e.g.
`[disconnect_tip] caller=reorg fork_h=N` vs
`caller=recovery fail_count=N`), so the next recurrence has a
forward-traceable log line in whatever journal window the operator
captures.

Minor gap: the writeup does not explicitly rule out the
`no_fork_reset` branch at `process_block.c:1917`, but that branch
resets to genesis (`h=0`), not to `h=3,081,407`, so it is trivially
excluded by the observed height. Worth one sentence for completeness.

## Question 2 (why BIP30 trips post-P8.9)

**Concur.**

Verified `coins_view_sqlite_open`'s sweep gate (`max_utxo_height >
tip_height`). After the one-time boot cleanup drives those into
equality, the gate closes on every subsequent boot — the sweep is an
*initialization*-time guard, not a runtime invariant. Nothing on the
runtime `disconnect_tip` path re-triggers the sweep, and P8.9 added
no runtime hook. The writeup correctly names this as the reason the
hotfix was "necessary but incomplete".

The Bitcoin Core comparison (line 186-198) is accurate and explains
why zclassicd is immune: `CDBBatch::Erase` turns a parent-cache erase
into a LevelDB DELETE automatically, whereas our
`cvc_batch_write` at `lib/coins/src/coins_view.c:255` is DIRTY-driven
and erase-blind. That asymmetry is the crux of the bug and was
captured correctly. No notes.

## Question 3 (the invariant)

**Concur with notes.**

The invariant is correctly phrased and spans both the cache
(`coins_tip.cache_coins`) and backing (SQLite `utxos`) layers. The
"equivalently" operational phrasing at lines 213-216 — "every output
created by any transaction in B must either be absent from
`coins_tip.cache_coins` AND absent from SQLite `utxos` after the next
`flush_coins_if_needed`" — is the directly-testable form and what
P10.1.3 should assert.

Two small sharpenings worth adding to the writeup (or encoding in the
fix's comment):

1. **Active-chain containment is necessary but not sufficient.** A
   stronger invariant: "if tx T at height H is resident in the coins
   view, and the active chain contains block B(H) with hash h, then
   B(H) contains T." This rules out the *other* half of the shape: T
   belongs to a block that was on the chain at height H but has been
   replaced by a different block at the same height after a reorg.
   The bug surface is the same DIRTY-gated flush — worth covering in
   the same property test.

2. **The fix's fit with existing code is clean.** The proposed
   DIRTY-pruned tombstone at the scratch layer matches
   `cvc_batch_write`'s pruned branch at `coins_view.c:265-278` and
   `coins_view_sqlite_batch_write_ex`'s pruned branch at
   `coins_view_sqlite.c:667-679` — both already exist and are
   exercised today. So the fix slots into an already-validated
   downstream path; only the upstream producer changes.

## Question 4 (test gap)

**Concur.**

Verified all three cited tests initialize their `coins_view_cache`
with a NULL backing:

- `test_chain_rollback.c:131-134` — `memset(&null_view, 0, ...)` +
  `coins_view_cache_init(&cache, &null_view)`.
- `test_reorg_safety.c` — same shape.
- `test_validation.c:1041-1100` — same shape, narrower scope.

With NULL backing, `coins_view_cache_have_coins` at
`lib/coins/src/coins_view.c:185-196` trivially returns false after
`coins_map_erase` (cache miss → fallthrough to `null_view.vtable ==
NULL` → return false at `coins_view.c:84`). The writeup is correct
that these tests cannot possibly have caught the leak — the backing
view that would have held the stale row simply does not exist in
their setup.

**One observation the writeup doesn't make explicitly:** the P10.1.1
repro test at `test_chain_stall_repro.c` (`1243e1766`) reproduces the
BIP30 trip *symptom* by directly poisoning a single cache via
`update_coins` + `coins_view_cache_set_best_block` (lines 225-229).
It does NOT invoke `disconnect_block`. That's fine for P10.1.1's
scope ("reproduce the trip shape deterministically"), but it means
the writeup's *causal* claim — that `coins_map_erase` at
`connect_block.c:639` is what leaves the coinbase in backing —
is not yet covered by any failing test. P10.1.3 must close that gap,
not just repeat the symptom reproduction at a different layer.

## Suggested test for P10.1.3

**File:** `lib/test/src/test_reorg_safety.c` (natural home — existing
multi-block fixtures and coinbase helpers; alternatively a new
`test_disconnect_block_purge.c` with shared helpers split out of
`test_chain_stall_repro.c`).

**Name:** `test_disconnect_block_purges_coinbase_from_backing`.

**Structure** (in the spirit of the writeup's pseudocode, resolved
against the real API):

```c
static int t_disconnect_purges_coinbase_from_backing(void)
{
    int failures = 0;

    TEST("disconnect_block: coinbase purges from parent cache after flush") {
        atomic_store(&g_deferred_proof_validation_below_height, -1);
        const int height = 200;

        /* ── Parent — the "coins_tip" proxy ────────────────── */
        struct coins_view_cache parent;
        struct coins_view null_view;
        memset(&null_view, 0, sizeof(null_view));
        coins_view_cache_init(&parent, &null_view);

        /* Build + apply the block's coinbase to parent — same
         * shape update_coins leaves coins_tip in after the
         * original connect_block. */
        struct uint256 prev_hash;
        memset(prev_hash.data, 0xC0, sizeof(prev_hash.data));
        struct block blk;
        make_block_seeded(&blk, height, &prev_hash, 0x00);
        update_coins(&blk.vtx[0], &parent, height);
        ASSERT(coins_view_cache_have_coins(&parent, &blk.vtx[0].hash));

        /* ── Scratch wraps parent — exact shape disconnect_tip
         *    builds at process_block.c:1671-1674. ────────── */
        struct coins_view parent_view;
        coins_view_cache_as_view(&parent_view, &parent);
        struct coins_view_cache scratch;
        coins_view_cache_init(&scratch, &parent_view);

        /* Coinbase has no inputs to restore → empty block_undo. */
        struct block_index bi;
        block_index_init(&bi);
        bi.nHeight = height;
        struct block_undo bu;
        block_undo_init(&bu);

        struct validation_state vs;
        validation_state_init(&vs);

        ASSERT(disconnect_block(&blk, &vs, &bi, &scratch, &bu));
        ASSERT(coins_view_cache_flush(&scratch));

        /* ── THE RED ASSERTION ──────────────────────────────
         * Today this fails — the scratch's coins_map_erase
         * was invisible to cvc_batch_write (no DIRTY flag). */
        ASSERT(!coins_view_cache_have_coins(&parent, &blk.vtx[0].hash));

        free_block(&blk);
        block_undo_free(&bu);
        coins_view_cache_free(&scratch);
        coins_view_cache_free(&parent);
        PASS();
    } _test_next:;

    return failures;
}
```

Helpers (`make_coinbase_seeded`, `make_block_seeded`, `free_block`) can
be reused from `test_chain_stall_repro.c` — either lifted into a
shared `test/helpers_chain_fixtures.h` or duplicated inline (test is
small; duplication is acceptable). A checkpoint fixture is NOT needed
because `disconnect_block` does not call into `check_block` — only
the coins-view mechanics are exercised.

## Other concerns (optional)

1. **P10.1.3 should also cover the second flush hop (scratch →
   coins_tip → SQLite).** The writeup's causal chain has three links:
   (a) scratch `coins_map_erase` fails to produce a DIRTY tombstone,
   (b) scratch flush into `coins_tip` therefore preserves the stale
   entry, (c) `coins_tip` flush into SQLite therefore never emits a
   DELETE. The test above closes (a) + (b). Link (c) could be
   validated by a follow-up test that uses a real `coins_view_sqlite`
   backing (in a temp directory) and asserts the SQLite `utxos` table
   no longer contains the coinbase row after a top-level
   `flush_coins_if_needed`. If that's out of scope for P10.1.3, the
   writeup should say so explicitly — `coins_view_sqlite_batch_write_ex`'s
   pruned branch at `:667` is already exercised by existing flush tests,
   which is a reasonable argument for skipping.

2. **Non-coinbase leak.** The "Note on disconnect_block's non-coinbase
   tx handling" at lines 240-252 correctly identifies that the same
   erase-without-tombstone bug applies to non-coinbase txs, and
   argues it is silent in practice because later-block spenders have
   already produced a pruned tombstone by the time disconnect runs.
   That's true today. But if P10.1.4's fix replaces `coins_map_erase`
   unconditionally (not gated on `is_coinbase`), it's strictly safer
   at zero extra cost. Worth calling out in P10.1.4's row so the fix
   doesn't add a case-split that the invariant doesn't require.

3. **Minor line-number nit in TL;DR.** The TL;DR cites
   `coins_view_sqlite.c:664` for the "flush only writes DIRTY entries"
   claim. `:664` is the DIRTY gate
   (`!(e->entry.flags & COINS_CACHE_DIRTY)` → continue); the pruned
   branch is at `:667`; the actual `sqlite3_step(stmt_delete_tx)` is
   at `:672`. Later in the doc (line 228) the writeup correctly cites
   `:667`. Harmless, but worth fixing in a follow-up edit if the
   postmortem is ever revised.

4. **Parent-cache-erase semantics worth documenting in the fix.**
   Our `cvc_batch_write` pruned branch at `coins_view.c:265-278`
   already promotes a DIRTY+pruned entry into the parent correctly;
   the SQLite flush then emits the DELETE via the path at
   `coins_view_sqlite.c:667`. Because the downstream plumbing is
   already well-shaped, the fix at `connect_block.c:639` can be
   minimal — which is the right outcome. A one-line comment at the
   fix site pointing to this review / the postmortem will help the
   next reader understand why the erase was replaced.
